# Avito.Kitchen

Backend-сервис для управления ресторанами, меню и заказами.

Проект реализован в рамках тестового задания Backend «Авито.Кухня».

Основная идея сервиса:

- ресторан управляет своим меню;
- пользователь создаёт заказ;
- ресторан принимает и изменяет статус заказа;
- сервис обеспечивает целостность данных при конкурентных изменениях.

# О проекте

Avito.Kitchen — backend-сервис для управления заказами в системе доставки еды.

Сервис предоставляет API для:

- получения списка ресторанов;
- получения меню ресторана;
- создания заказа пользователем;
- изменения статусов заказа рестораном;
- просмотра заказов ресторана.

Проект построен как **modular monolith** с разделением ответственности между слоями:
HTTP
|
Service
|
Repository
|
PostgreSQL

Бизнес-логика находится в сервисном слое, а работа с данными изолирована через интерфейсы репозиториев.

---

# Бизнес-сценарии

## Пользователь создаёт заказ

Сценарий:

1. Пользователь получает список ресторанов.
2. Пользователь получает меню выбранного ресторана.
3. Пользователь создаёт заказ.
4. Заказ получает статус `CREATED`.
5. Ресторан начинает обработку заказа.

---

## Ресторан изменяет статус заказа

Жизненный цикл заказа:
CREATED
|
v
ACCEPTED
|
v
PREPARING
|
v
READY
|
v
COMPLETED

Каждый переход статуса проверяется бизнес-логикой сервиса.

- преобразование DTO;
- формирование ответов.

# Почему modular monolith

Для текущего масштаба задачи выбран **modular monolith**.

## Преимущества

- простота разработки;
- единое хранилище данных;
- отсутствие сложностей распределённой системы;
- возможность дальнейшего выделения сервисов.

Такой подход позволяет сохранить хорошее разделение ответственности без преждевременного усложнения архитектуры.

# Работа с заказами

## Транзакционность

Создание заказа выполняется внутри одной транзакции.

В рамках операции:

1. Проверяется существование ресторана.
2. Проверяется наличие элементов меню.
3. Создаётся заказ.
4. Создаются элементы заказа.
5. Фиксируется состояние заказа.

Это гарантирует **атомарность** операции.

---

## Конкурентный доступ

Для защиты от конкурентных изменений используются блокировки PostgreSQL.

### `SELECT FOR SHARE`

Используется при чтении:

- ресторана;
- меню.

Позволяет гарантировать согласованность данных во время создания заказа.

### `SELECT FOR UPDATE`

Используется при изменении состояния заказа.

Позволяет избежать конфликтующих обновлений статуса.

---

## Snapshot заказа

При создании заказа информация о товарах сохраняется в `order_items`.

Это позволяет сохранить историю заказа даже если меню ресторана изменится.

# Хранение данных

Используется **PostgreSQL**.

## Основные таблицы

- `restaurants`
- `menu_items`
- `orders`
- `order_items`
- `order_statuses`

---

### Таблица `orders`

Хранит:

- пользователя;
- ресторан;
- текущий статус;
- дату создания.

### Таблица `order_items`

Хранит snapshot товаров заказа:

- название;
- цена;
- количество.

# Пагинация

Для списка заказов ресторана используется **cursor pagination**.

## Преимущества

- стабильная выдача при изменении данных;
- отсутствие проблем OFFSET pagination на больших таблицах;
- эффективная работа с индексами.

Используется сортировка по:

- `created_at`
- `id`

Для этого добавлены необходимые индексы.

# Ограничения масштабирования

Текущая архитектура рассчитана на один сервис.

При увеличении нагрузки возможны следующие улучшения:

## Очередь сообщений

Для асинхронных событий:

- изменение статуса заказа;
- уведомления ресторана;
- события доставки.

Можно использовать **Kafka** / **RabbitMQ**.

## Кэширование

Для часто читаемых данных:

- список ресторанов;
- меню.

Можно добавить **Redis**.

## Выделение сервисов

При росте нагрузки возможное разделение:

- **Restaurant service**
- **Order service**
- **Notification service**

Текущий modular monolith позволяет сделать такое выделение постепенно.
