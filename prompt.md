Проект представляет собой MVP сервиса доставки еды «Авито.Кухня».

Главная цель проекта — не создание production-ready аналога полноценного сервиса доставки, а демонстрация моего подхода к проектированию backend-систем, моделированию данных, проектированию API, написанию поддерживаемого кода, тестированию и документированию технических решений.

### Выбранный стек

* Go;
* PostgreSQL;
* REST API;
* Docker Compose;
* SQL-миграции;
* OpenAPI;
* golangci-lint;
* PlantUML для CJM и архитектурных диаграмм.

### Основные участники системы

В системе существуют две основные стороны.

#### Пользователь

Пользователь может:

* получить список доступных заведений;
* открыть меню выбранного заведения;
* увидеть доступность позиций меню;
* создать заказ;
* получить информацию о заказе;
* отслеживать изменение статуса заказа.

#### Заведение

Заведение может:

* управлять своим меню;
* добавлять и изменять позиции меню;
* изменять доступность позиции;
* получать поступившие заказы;
* принимать или отклонять заказ;
* изменять статус заказа.

Авторизация и аутентификация пользователей и заведений намеренно не реализуются, так как находятся за пределами MVP согласно условиям задания.

### Основные сущности

Необходимо использовать следующие основные сущности:

* Restaurant;
* MenuItem;
* Order;
* OrderItem.

### Жизненный цикл заказа

Базовый успешный сценарий:

CREATED → ACCEPTED → PREPARING → READY → COMPLETED

Сценарий отказа:

CREATED → REJECTED

Система должна проверять допустимость переходов между статусами.

Например:

* CREATED → ACCEPTED — допустимо;
* ACCEPTED → PREPARING — допустимо;
* PREPARING → READY — допустимо;
* CREATED → READY — недопустимо;
* COMPLETED → CREATED — недопустимо.

Недопустимый переход должен приводить к соответствующей доменной ошибке.

### Сохранение информации о заказе

OrderItem должен хранить снимок информации о товаре на момент оформления заказа.

В частности необходимо сохранять:

* название позиции;
* цену позиции;
* количество.

Это необходимо для того, чтобы изменение рестораном названия или стоимости MenuItem после оформления заказа не изменяло историю уже созданного заказа.

### Интеграция с заведением

В репозитории должен находиться отдельный демонстрационный сервис заведения.

Он должен:

* запускаться вместе с основным приложением через Docker Compose;
* взаимодействовать с основным сервисом по HTTP;
* демонстрировать работу API, предназначенного для заведений.

Необходимо избегать избыточной сложности интеграции в рамках MVP.

### Принципы разработки

При помощи мне в разработке придерживайся следующих правил.

1. Начинай проектирование с бизнес-сценариев, а API выводи из этих сценариев.

2. Не усложняй MVP без необходимости.

3. Всегда разделяй:

   * то, что действительно реализуется в MVP;
   * возможные улучшения production-версии.

4. Используй простой и идиоматичный Go.

5. Бизнес-логика не должна зависеть напрямую от HTTP-слоя.

6. Логику работы с PostgreSQL необходимо отделять от бизнес-логики.

7. Для бизнес-ошибок необходимо использовать явные ошибки доменного уровня.

8. Там, где требуется атомарность нескольких операций с БД, необходимо использовать транзакции.

9. Для каждого HTTP endpoint необходимо продумывать:

* входные параметры;
* request body;
* response body;
* HTTP status code;
* возможные ошибки.

10. OpenAPI-спецификация должна соответствовать реально реализованному API.

11. SQL-миграции являются источником истины для схемы базы данных.

12. Основную бизнес-логику необходимо покрыть unit-тестами.

13. Критичные пользовательские сценарии желательно покрыть интеграционными тестами.

14. Все компоненты проекта должны запускаться одной командой:

docker compose up 
её нужно прописать в Makefile

15. Все сознательные упрощения MVP необходимо описывать в README.

16. Перед написанием компонента сначала объясняй:

* зачем он нужен;
* какую ответственность несёт;
* от каких компонентов зависит.

17. Если существует несколько разумных архитектурных решений, сначала кратко сравни их преимущества и недостатки.

18. Не принимай архитектурное решение вместо меня без объяснения.

19. Не добавляй без необходимости:

* Kafka;
* RabbitMQ;
* Redis;
* микросервисную архитектуру;
* Kubernetes;
* сложные паттерны;
* дополнительные абстракции.

20. При этом отмечай потенциальные проблемы, которые возникнут при масштабировании системы:

* конкурентные запросы;
* повторное создание заказов;
* идемпотентность;
* согласованность данных;
* отказ внешнего сервиса заведения;
* высокая нагрузка на БД.

21. Если проблема не требует решения в рамках MVP, предложи оставить её как осознанное ограничение и описать возможное production-решение в README.
