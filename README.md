## Business scenarios

Проект покрывает основные пользовательские сценарии:

- просмотр заведений;
- просмотр меню;
- создание заказа;
- обработка недоступных позиций;
- просмотр и отслеживание заказа.

Со стороны заведения поддерживаются:

- управление меню;
- управление доступностью позиций;
- получение заказов;
- принятие и отклонение заказов;
- изменение статуса заказа.

## Architecture

Avito.Kitchen реализован как модульный монолит на Go с PostgreSQL в качестве основного хранилища данных.

В рамках MVP основной сервис является источником истины для заведений, меню и заказов. Демонстрационный сервис заведения не имеет прямого доступа к PostgreSQL и взаимодействует с Avito.Kitchen исключительно через REST API.

Внутри основного приложения используется простое разделение ответственности:

```text
HTTP transport
      ↓
Application services
      ↓
Repositories
      ↓
PostgreSQL

Application services
      ↓
Domain
```

HTTP-слой отвечает за получение и валидацию входных данных, вызов бизнес-логики и преобразование доменных ошибок в HTTP-ответы.

Application service реализует пользовательские сценарии и координирует работу доменной логики и хранилища.

Domain содержит основные бизнес-сущности, статусы заказа и правила допустимых переходов между ними.

Repository инкапсулирует взаимодействие с PostgreSQL.

### Why modular monolith

Для MVP выбран модульный монолит вместо микросервисной архитектуры.

Функциональность проекта пока невелика, а разделение Restaurant, Menu и Order на независимые сетевые сервисы потребовало бы решения дополнительных инфраструктурных задач: межсервисного взаимодействия, обработки частичных отказов, наблюдаемости, версионирования контрактов и согласованности распределённых данных.

Эта сложность не оправдана текущими требованиями MVP.

При этом логические границы предметных областей сохраняются в структуре приложения, что позволяет в будущем выделить наиболее нагруженные части системы в независимые сервисы.

Основное приложение остаётся stateless и при необходимости может горизонтально масштабироваться запуском нескольких экземпляров за балансировщиком нагрузки.

### Go module structure

Несмотря на наличие двух запускаемых сервисов, репозиторий использует один Go module.

В рамках MVP это упрощает управление зависимостями, локальную разработку, тестирование и сборку проекта.

При этом Avito.Kitchen и Demo Restaurant являются отдельными приложениями:

```text
cmd/api
cmd/restaurant-demo
```

Они собираются в независимые бинарные файлы и запускаются в отдельных Docker-контейнерах.

Наличие общего Go module не используется для обхода архитектурной границы между сервисами. Demo Restaurant не обращается напрямую к repository, domain или PostgreSQL основного приложения и взаимодействует с Avito.Kitchen только по HTTP.

Если сервис заведения в дальнейшем получит независимый жизненный цикл, собственную команду разработки или существенно отличающийся набор зависимостей, его можно будет выделить в отдельный Go module или отдельный repository.

### Restaurant integration

В MVP используется pull-based модель интеграции.

Demo Restaurant периодически запрашивает у Avito.Kitchen новые заказы со статусом `CREATED`.

Получение заказа не изменяет его состояние. После принятия решения заведение отдельным HTTP-запросом изменяет статус:

```text
CREATED → ACCEPTED
```

или:

```text
CREATED → REJECTED
```

После начала приготовления заведение последовательно выполняет переходы:

```text
ACCEPTED → PREPARING → READY → COMPLETED
```

Avito.Kitchen остаётся источником истины для состояния заказа, поэтому пользователь получает актуальный статус заказа непосредственно из основного сервиса.

Pull-based интеграция выбрана как сознательное упрощение MVP. Она позволяет продемонстрировать API интеграции с заведением без добавления брокеров сообщений, webhook delivery, retry-механизмов и инфраструктуры гарантированной доставки событий.

### Scaling limitations

При существенном росте нагрузки текущая архитектура имеет несколько ожидаемых ограничений.

PostgreSQL станет общей точкой нагрузки для чтения меню, создания заказов и получения их статусов. Возможные направления масштабирования включают оптимизацию индексов и запросов, read replicas, кэширование, partitioning и при необходимости sharding.

Polling со стороны большого количества заведений создаст значительное число запросов даже при отсутствии новых заказов. В production-системе pull-модель может быть заменена webhooks или асинхронной доставкой событий через message broker.

Повторный `POST` создания заказа после сетевого timeout может привести к созданию дубликатов. Production-версия должна поддерживать идемпотентность создания заказа, например с помощью `Idempotency-Key`.

Текущая модель доступности позиции хранит только признак доступности и не реализует количественные остатки или резервирование. При добавлении складского учёта потребуется защита от конкурентной продажи одного остатка нескольким пользователям.

Модульный монолит масштабируется как единое приложение. Если разные функциональные области начнут значительно отличаться по профилю нагрузки, отдельные модули могут быть выделены в независимо масштабируемые сервисы.
